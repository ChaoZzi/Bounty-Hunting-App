## 01 · 2026-11-24 · 分类表和任务表通过什么字段关联

**结论**：`t_task.category_id` → `t_task_category.id`，多对一，但**没有物理外键**。

**要点**

- 关联字段只有 `category_id` 一个。
- 建表时故意不写 `FOREIGN KEY`，一致性由应用层保证。
  - 原因：写性能、分库分表不支持、DDL 变更困难。
  - 代价：数据库拦不住「指向不存在的分类」这种脏数据。
- `category_id` 的默认值是 `0`，而分类表里没有 id=0 的记录。
  - 所以关联查询**必须用 `LEFT JOIN`**；用 `INNER JOIN` 会把这些任务静默过滤掉。
- 现有代码只做了「按分类过滤」，没做「显示分类名」：
  - 已实现：`GET /task/hall?categoryId=2`
  - 未实现：分类列表接口、`TaskCardVO.categoryName`
- 索引 `idx_category (category_id, status)` 已覆盖按分类查任务的场景。

**示例**

```sql
SELECT t.id, t.title, t.unit_price, c.name AS category_name
FROM t_task t
LEFT JOIN t_task_category c ON t.category_id = c.id
WHERE t.status = 2 AND t.deleted = 0
ORDER BY t.weight DESC, t.created_at DESC;
```

**相关文件**：`server/db/schema.sql`、`server/bounty-dao/.../entity/Task.java`

## 02 · 2026-11-24 · 手机截图怎么让我识别到

**结论**：最省事的是我直接用 adb 拉取，你正常截图即可，不需要传文件。

**要点**

- 三种方式：
  - **① 我拉取**（推荐）：你截图 → 我从手机目录 `adb pull` 最新一张
  - **② 我截屏**：`adb exec-out screencap` 直接抓当前屏幕，你什么都不用做
  - **③ 拖进聊天框**：适合不方便插线时
- 前置条件：手机插着 USB 且已授权（`adb devices` 显示 `device`）
- 截图目录：`/sdcard/Pictures/Screenshots/`
- 拉取的是**最新**一张；要看指定某张需说明时间或文件名

**示例**

```powershell
adb shell "ls -t /sdcard/Pictures/Screenshots/*.jpg | head -1"
adb pull /sdcard/Pictures/Screenshots/Screenshot_xxx.jpg D:\dev\latest-shot.jpg
```

**相关文件**：`scripts/run-app.ps1`（同样依赖 adb 通道）

## 03 · 2026-11-24 · 数据库是怎么连的，在项目哪里体现

**结论**：连接信息**只存在于两个 yml 文件里**，Java 代码里一行连接配置都没有，全靠 Spring Boot 自动配置。

**要点**

- 配置位置（就这两处）：
  - `server/bounty-boot/src/main/resources/application-local.yml` → `spring.datasource.*`（url / 用户名 / 密码）
  - 同目录 `application.yml` 第 13 行 `spring.profiles.active: local` → 决定加载哪个 profile
- 代码里没有 `new Connection()`，也没有 `@Autowired DataSource`：
  - Spring Boot 读 `spring.datasource.*` 自动创建 HikariCP 连接池
  - MyBatis-Plus starter 自动创建 `SqlSessionFactory`
  - 我们只写 Mapper 接口，不写实现类
- 三个把「表」和「类」绑起来的注解：

| 注解 | 位置 | 作用 |
|---|---|---|
| `@TableName("t_user")` | 实体类 | 类 → 表 |
| `@TableId(type = IdType.AUTO)` | 主键字段 | 自增 |
| `@TableLogic` | `deleted` 字段 | 逻辑删除，查询自动加 `deleted=0` |

- 字段映射靠 `mybatis-plus.configuration.map-underscore-to-camel-case: true`：`unit_price` ↔ `unitPrice`，不用手写 `@TableField`
- Mapper 扫描：启动类上的 `@MapperScan("com.bounty.dao.mapper")`
- 分页必须手写插件：`MybatisPlusConfig` 里的 `PaginationInnerInterceptor`，漏了会导致 `total` 恒为 0
- 数据库实体在哪：**本机原生 PostgreSQL 16**（服务名 `postgresql*`），端口 `5432`，库名 `bounty`，用户 `bounty`
  - 备选：`docker-compose.yml` 里也有一个 `postgres` 容器，映射到 `5433`，本机没装 PG 时可用
  - 数据文件：原生 PG 在它自己的 data 目录；容器版在 `data/postgres/`

**为什么有两个 PostgreSQL**

本机已经装了原生 PostgreSQL 16（5432），`start-all.ps1` 会优先用本机服务启动，省一个容器。
容器版映射到 5433 是为了不和原生抢端口，只有本机没装 PG 时才会用到。

**换回容器版要改什么**

只改 `application-local.yml` 的 url 端口和账号：

```yaml
url: jdbc:postgresql://localhost:5433/bounty?stringtype=unspecified
username: bounty
password: bounty123456
```

**改连接信息只改一处**

想连远程数据库或改密码，只动 `application-local.yml` 的 `spring.datasource` 三行，然后重启后端即可。代码不用碰。

**相关文件**：`application-local.yml`、`application.yml`、`BountyApplication.java`、`MybatisPlusConfig.java`、`bounty-dao/pom.xml`、`docker-compose.yml`

## 04 · 2026-11-26 · 21 张表各是干什么的，彼此什么关系

**结论**：按业务分五个域——用户 4 张、任务 4 张、资金 4 张、增长 2 张、运营系统 7 张。所有关联靠 `*_id`，**没有物理外键**。

**要点**

- 核心主线只有一条：

  ```
  t_user --发布--> t_task --报名--> t_task_order --提交--> t_task_submission
                                        └--审核--> t_task_review_log
  t_task_order --审核通过--> t_wallet_flow（钱进钱包）
  ```

- 钱包相关三张表分工：
  - `t_wallet` = 余额快照（可用 / 冻结 / 待结算）
  - `t_wallet_flow` = **账本，唯一真相**，`biz_no` 防重复记账
  - `t_withdraw` = 出款单据
- 角色不是账号类型：`t_user` 没有 `user_type` 字段，能不能发任务只看 `realname_status = 2`
- `t_task_order` 冗余了 `publisher_id` 和 `amount`：
  - 前者避免查订单还要 JOIN 任务表
  - 后者锁定成交价，悬赏主事后加价不影响已报名的单
- 21 张里只有 6 张有数据，其余是建好、等对应功能实现的空表

**详细版**：`docs/数据库设计说明.md`（含 ER 图、逐表字段、三条跨表规则）

**相关文件**：`server/db/schema.sql`

## 05 · 2026-11-26 · 邀请表支持「一个用户邀请多个好友」

**结论**：**已经支持**。`t_invite.inviter_id` 没有唯一约束，还专门建了索引；唯一的约束在 `invitee_id` 上。

**要点**

- 两个约束各管一件事：

  | 约束 | 作用 | 去掉的后果 |
  |---|---|---|
  | `UNIQUE (invitee_id)` | 一个新人只能被邀请一次 | 同一个人被两人各领一次奖，平台重复付钱 |
  | `INDEX (inviter_id, created_at)` | 加速「我邀请了谁」 | 邀请人多时全表扫描 |

- 邀请关系存了两处：`t_user.inviter_id`（关系）+ `t_invite`（奖励发放状态）
  - 好处：查「谁邀请了我」不用再查表
  - 代价：两处可能不一致，**注册时必须在同一个事务里同时写**
- 当前 `AuthService.loginOrRegister()` 只写了 `t_user.inviter_id`，`t_invite` 还没写，做邀请功能时要补
- 邀请排行榜用现有结构直接能算，不需要改表

**决定**：暂不加渠道来源字段（`source`：poster / link / manual），等做渠道分析时再补。

**相关文件**：`server/db/schema.sql`、`bounty-service/.../AuthService.java`
