## 二、逐屏拆解

### 1. 我的任务

**结构**：4 个 Tab（进行中/待审核/已通过/未通过）→ 顶部提示「仅保留最近 7 天」→ 卡片列表 → 悬浮球「后续任务」

**每张卡片的信息层级**（从上到下）：

```
任务名（左）                     +1.58元（右，红色，最大字号）
报名时间 2026-11-11 13:32:37（灰）
任务已超时（红）
                          [删除记录] [重新报名]
官方提示：此任务需要满足18岁以上（红，小字）
```

**值得抄**

- 金额绝对突出，比任务名还显眼
- 每张卡都有**两个动作按钮**，不是点进去才知道能干什么
- 「官方提示」做成卡片内的红字，把年龄/资质限制前置
- 黄色圆形角标「极速快审」直接盖在头像上，一眼识别

**我方差距**

| 缺什么 | 说明 |
|---|---|
| 重新报名 | 后端已支持（复用原单 1←4/5），前端没接 |
| 删除记录 | 后端没有接口，需要新增 `DELETE /order/{no}` |
| 极速快审角标 | `t_task.fast_review` 字段已有，VO 没透出 |
| 7 天保留规则 | 后端没实现，目前是全量返回 |

### 2. 悬赏大厅

**结构**：顶部工具条（屏蔽已做 / 搜索框 / 发布悬赏）→ 筛选行（类型▾ + 综合/最新/简单/高价/精选）→ 任务列表 → 悬浮球「我的接单」

**列表项布局**：

```
[头像] 任务标题 [火][快审]              +0.37元
       [淘宝-DDG旗舰店]          4667人已赚  剩余1600个
```

**值得抄**

- **双行信息密度**：第一行给「是什么」，第二行给「谁发的 + 多少人在做 + 还剩多少」
- 「剩余名额」是决策关键，必须和金额同一屏看到
- 「顶」用红色方标钉在标题后，比排序更直观
- 「屏蔽已做」是个很实用的开关，避免刷到自己做过的

**我方差距**

- 筛选栏只有 4 个 sort，没有「类型▾」下拉（分类接口还没做）
- 列表只显示 `takenQuota` 和 `remainQuota`，没有来源标签（我们没这个字段，可不做）
- 没有「顶」「快审」角标
- 没有悬浮球

### 3. 我的

**结构**：红色渐变头部（头像+年卡 / 昵称 / ID / 信誉分进度条）→ 会员横幅 → 资产三宫格 → 两个大按钮（我的报名 / 发布管理任务）→ 广告位 → 功能列表 → 底部 Tab

**值得抄**

- **信誉分做成进度条**（2100/10000），比一个数字有压力感
- 资产三宫格：赏金 / 奖励 / 余额，各自带动作按钮（兑换/兑换/查看）
- 「我的报名」和「发布/管理任务」并排，**双角色入口**一眼可见
- 功能列表项少而精：邀请、举报、消息、收益、设置

**我方差距**

| 缺什么 | 对应字段/表 |
|---|---|
| 信誉分进度条 | `t_user.credit_score` 已有（上限 10000） |
| 赏金 / 奖励 分离 | 目前只有 `t_wallet` 的 available，没分「赏金」「奖励」 |
| 双角色大按钮 | 只有文字列表项，没有大按钮 |
| 会员 | 表没有，`member_level` 字段预留了 |

### 4. 首页

**结构**：Banner → 金刚区 5 个图标 → 公告条 → Tab（推荐悬赏/极速快审）→ 任务流

**值得抄**

- 金刚区是「运营位」，可以随时换成活动入口
- 公告条单独一条，滚动显示，不占大块空间

**优先级**：P1。功能上等价于「大厅 + 运营位」，可以复用同一套任务卡片组件。

### 5. 更多赚钱

第三方导流（闲玩、多游、我玩、点团帮），底部明确写「以上服务非赏帮赚所有，由其他公司平台提供」。

**我方**：不做。这是流量变现手段，需要商务对接，跟 MVP 无关。

### 6. 管理悬赏（悬赏主端）

**这是全篇信息量最大的一屏，也是平台主要收入来源。**

**结构**：

```
Tab：待上架 | 展示中(5) | 已暂停(1) | 审核失败
搜索：输入项目名称、ID、备注
提示：使用置顶和刷新，获得更多浏览曝光量
────────────────────────────────
任务卡：
  攒粒(0.50元)                    [待审核(0)]
  浏览次数:1346次
  悬赏名额:180个  已完成:130个  剩余:31个
  [置顶][刷新][定时置顶][自动刷新][刷新包]
  [置顶包][加价][加量][快审中][暂停]
  查看官方提示 ▾
```

**值得抄**

- 每张卡 10 个操作按钮，全部是**付费增值服务**
- 数据展示三件套：浏览次数 / 名额 / 完成进度
- 「待审核(0)」红色角标直接显示待办数量
- 「快审中」是状态按钮（已开通），与「快审」区分

**我方现状**

好消息是**数据库已经准备好了**：

| 功能 | 对应表/字段 |
|---|---|
| 置顶 | `t_task.top_until` + `weight` |
| 快审 | `t_task.fast_review` |
| 加量 | `t_task.total_quota` / `remain_quota` |
| 加价 | `t_task.unit_price` |
| 增值订单 | `t_promotion_order`（类型枚举已定义 8 种） |
| 浏览数 | `t_task.view_count` |

缺的是**接口和页面**。

### 7. 任务详情（最新截图）

**结构**：任务描述 → 任务步骤（编号列表，每步嵌操作按钮）→ 上传数据图 → 最近截图 → 底部固定条（换一个 + 提交任务 + 倒计时）

**值得抄（这条最值得）**

- **步骤内嵌按钮**：「打开链接」「复制链接」「复制数据」直接放在步骤里，用户不用跳出去找
- **复制数据做成红色大按钮**：因为这类任务的核心动作就是复制邀请码
- **上传区直接显示「最近截图」**：省掉从相册翻找的动作，大幅降低操作成本
- **底部倒计时**：`提交任务(倒计时:0时59分47秒)`，制造紧迫感

**我方差距**

`task_detail_page.dart` 目前只有：标题、金额、名额、任务要求、完成时限 + 「立即报名」按钮。

缺：
- `steps` 字段的可视化（DB 里有 JSON，前端没渲染）
- 报名后的「提交凭证」入口
- 倒计时

## 三、值得抄的 8 个设计点

| # | 设计 | 为什么 |
|---|---|---|
| 1 | 金额字号最大 | 用户唯一的决策依据 |
| 2 | 剩余名额与金额同屏 | 制造稀缺感 |
| 3 | 卡片内直接给动作按钮 | 少一次点击 |
| 4 | 「官方提示」红字内置 | 提前过滤不符合条件的用户，减少无效提交 |
| 5 | 信誉分用进度条 | 可视化成长，比数字有驱动力 |
| 6 | 双角色入口并排 | 支持「先接单后发单」的转化路径 |
| 7 | 上传区直接列最近截图 | 减少操作步骤 |
| 8 | 倒计时固定在底部 | 紧迫感 + 防止忘记提交 |

## 四、明确不抄的 5 个点

| # | 设计 | 不抄的原因 |
|---|---|---|
| 1 | 满屏红色 + 大色块 | 廉价感，与「黑金」定位冲突 |
| 2 | 悬浮球堆叠（3 个） | 遮挡内容，单手操作易误触 |
| 3 | 广告位塞进个人中心 | 破坏信息层级 |
| 4 | 「更多赚钱」导流页 | 需要商务合作，与 MVP 无关 |
| 5 | 免责声明那一套 | 我们不接第三方 CPA |

## 五、对排期的启示

按「收入贡献」排序，而不是按「界面好看」排序：

| 优先级 | 功能 | 理由 |
|---|---|---|
| **P0** | 提交凭证 + 审核 + 结算 | 跑通闭环，没有它整个产品不成立 |
| **P1** | 悬赏主发布 + 管理悬赏（含 10 个增值操作） | **平台唯一收入来源** |
| **P1** | 我的任务补齐（重报、删除） | 留存相关，用户会反复用 |
| P2 | 首页运营位（Banner、金刚区、公告） | 纯展示，可后补 |
| P2 | 分类筛选、快审/顶角标 | 锦上添花 |
| P3 | 邀请、会员、收益统计 | 有量之后才有意义 |

**「管理悬赏」这一屏应该被重视**——它决定了平台能不能赚钱，但做起来全是业务规则（置顶到期、刷新包扣次、加价改单价），比 UI 复杂得多。

## 六、发布任务流程（2026-11-24 补充）

截图 5 张，完整走了一遍悬赏主发布任务的过程。**这一组图信息量最大，因为它暴露了整个产品的业务模型。**

### 6.1 完整流程

```
选发布类型 → 填任务信息 → 编辑步骤 → 预览 → 申请发布 → 平台审核 → 上架
```

注意第三张图底部按钮是「**申请发布**」而不是「发布」——说明发布不是即时的，要过平台审核。

### 6.2 发布类型选择页

分三档，**价格下限不同**，用这个引导悬赏主定价：

| 分类 | 类型 | 起价 |
|---|---|---|
| 发布高价悬赏 | 下载体验 | 0.50 元起 |
| | 认证绑卡 | 0.50 元起 |
| | 电商相关 | 0.50 元起 |
| | 时间较长 | — |
| 发布简单悬赏 | 简单帮忙 | — |
| | 账号注册 | 0.15 元起 |
| 发布其他悬赏 | 后续回收 | — |
| | 不易完成 | — |

**规则第一条**：「必须完成悬赏主实名认证，才能发布悬赏任务」——和我们定的规则一致。

### 6.3 表单字段清单（★ = 我们表里还没有）

| 字段 | 取值 | 我方现状 |
|---|---|---|
| 项目名称 | 文本（如「攒粒」） | `title` ✓ |
| 悬赏标题 | 文本 + emoji | — |
| 任务描述 | 一句话 | `intro` ✓ |
| 提交时间 | 限制 N 小时内提交 | `deadline_minutes` ✓ |
| **审核时间** | 限制 N 天内审核，**超时自动通过** | ❌ 缺 |
| **设备类型** | 全部 / 安卓 / 苹果 | ❌ 缺 |
| **地区** | 全部 / 指定 | ❌ 缺 |
| **做单次数** | 屏蔽同类 / 仅限一次 / 每日一次 / 每人多次 | ⚠️ 只有一个 `limit_per_user` |
| 重复次数 | 数字 | ⚠️ 同上 |
| 推送联盟 | 是 / 否 | 不需要（我们不做联盟） |
| 悬赏单价 | 金额 | `unit_price` ✓ |
| 悬赏名额 | 数量 | `total_quota` ✓ |
| **预付赏金** | 单价 × 名额 + 服务费 | ❌ 缺（资金模型关键） |

### 6.4 三个最关键的发现

**① 预付赏金模型**

```
预付赏金 225.50 元 = 0.50 元 × 410 个 + 服务费
```

悬赏主**必须先付钱才能发任务**，付的是「单价 × 名额 + 服务费」。

这解释了几件事：

- 为什么悬赏主端有「充值」——他得先有钱
- 为什么平台不怕悬赏主跑路——钱已经收进来了
- 为什么有「加量」这个增值服务——名额用完了，要再付一次钱才能加

**我方影响**：`t_task` 缺少「预付金额」「已冻结金额」的概念。当前设计是「悬赏主发任务不扣钱」，将来结算时会发现平台在垫钱。这个必须补。

**② 审核超时自动通过**

> 审核时间：限制1天内审核，**若未按时审核，将自动通过**

这是一条极其重要的保护规则。如果没有它，悬赏主只要不审核，用户就永远拿不到钱，平台会变成黑洞。

**我方影响**：`t_task` 需要加 `review_deadline_minutes`，`t_task_order` 需要能算出审核截止时间，定时任务要加一条「超时自动通过」。

我们现在只有「超时关单」（1→5），没有「超时自动结算」（2→3）。**这条不做，功能 3 就闭不了环。**

**③ 步骤是结构化内容，不是纯文本**

添加步骤时可选 7 种内容类型：

| 类型 | 渲染成什么 |
|---|---|
| 输入网址 | 文字 + 「打开链接」按钮 |
| 传二维码 | 二维码图片 + 「保存图片」 |
| 图文说明 | 图片 + 文字 |
| 文字说明 | 纯文字 |
| 复制数据（如邀请码） | 文字 + 「复制数据」按钮 |
| 收集截图 | 上传区（接单方提交时用） |
| 收集信息 | 表单（姓名/手机号等） |

**我方现状**：`t_task.steps` 是 `JSON`，但结构只有 `[{"step":1,"desc":"..."}]` —— **没有 type 和 payload**，前端无法渲染出按钮、二维码、上传区。

正确结构应该类似：

```json
[
  { "type": "text",   "desc": "下载心遇 App" },
  { "type": "link",   "desc": "点击下载", "url": "https://..." },
  { "type": "copy",   "desc": "注册时填邀请码", "value": "4K79ANB5" },
  { "type": "image",  "desc": "示例截图", "url": "/files/xxx.jpg" },
  { "type": "upload", "desc": "上传实名认证截图", "max": 1 }
]
```

### 6.5 数据库差距汇总

| 表 | 要加什么 | 用途 |
|---|---|---|
| `t_task` | `review_deadline_minutes` | 审核超时自动通过 |
| `t_task` | `device_limit`（0全部/1安卓/2苹果） | 设备限制 |
| `t_task` | `region_limit`（JSON 或 0=全部） | 地区限制 |
| `t_task` | `take_times_type`（0屏蔽同类/1仅一次/2每日一次/3多次） | 做单次数 |
| `t_task` | `prepaid_amount` / `frozen_amount` | 预付与冻结 |
| `t_task` | `steps` 结构升级（加 type/payload） | 步骤渲染 |
| `t_wallet` | 已有 `frozen`，但语义是「提现冻结」 | 需区分「任务预付冻结」 |
| 新表 | `t_task_step`（或继续用 JSON） | 步骤存 JSON 更简单，建议后者 |

### 6.6 建议的落地顺序

**不要现在改表。** 你正在写功能 2（提交凭证），改表会强制重建数据库、打断进度。

推荐节奏：

```
现在        功能 2：提交凭证（不涉及新字段）
下一步      功能 3：审核 + 结算 ← 必须加 review_deadline_minutes
之后        功能 4：悬赏主发布 ← 一次把剩下 5 个字段补齐
最后        功能 5：管理悬赏 + 增值服务
```

功能 3 只需要加 1 个字段，改动最小；功能 4 一次性加 5 个，那时候再重建数据库不心疼。

### 6.7 可以直接抄的两个交互

**① 预览**

发布页底部有「预览」按钮，让悬赏主切换成接单方视角看效果。

这一个按钮能消灭大量「发布完才发现步骤写错了」的客服成本。**做发布页时一定要做。**

**② 步骤支持拖动排序 + 侧滑删除**

长按拖动调整顺序，向两侧滑动移除。比「点进编辑→删除→返回」少三步。
