## 三、逐表说明

### 3.1 用户域

#### `t_user` 账号主表

一个手机号一行。C 端和 B 端（悬赏主）共用，**没有"用户类型"字段**。

| 关键字段 | 含义 |
|---|---|
| `phone` | 登录账号，唯一 |
| `credit_score` | 信誉分 0–10000，初始 1000 |
| `realname_status` | 0未认证 / 1审核中 / 2已认证 / 3失败 —— **发布任务的唯一门槛** |
| `is_publisher` | 是否发布过任务（只用于展示，不做权限判断） |
| `invite_code` | 我的邀请码，注册时生成 |
| `inviter_id` | 谁邀请了我 |
| `member_level` / `member_expire_at` | 会员（预留） |
| `deleted` | 逻辑删除 |

> **角色 = 权限，不是账号类型。** 能不能发任务只看 `realname_status = 2`，不靠 `is_publisher`。

#### `t_user_realname` 实名认证（与 user 1:1）

| 关键字段 | 含义 |
|---|---|
| `real_name` / `id_card_cipher` | **AES-GCM 密文**，不存明文 |
| `id_card_hash` | SHA256，用来做「一证一号」唯一约束 |
| `id_card_mask` | 脱敏展示，如 `3301**********1234` |
| `status` | 1审核中 / 2通过 / 3驳回 |

> 为什么要 `hash` 又存 `cipher`：`cipher` 用于必要时解密核对，`hash` 用于唯一索引——密文每次加密结果不同，没法直接做唯一约束。

#### `t_wallet` 钱包（与 user 1:1，`user_id` 就是主键）

| 字段 | 含义 |
|---|---|
| `available` | 可用余额 |
| `frozen` | 冻结（提现处理中 / 任务预付冻结） |
| `pending` | 待结算（任务审核中） |
| `total_income` / `total_withdraw` | 累计收入 / 累计提现 |
| `version` | 乐观锁 |

> **余额是快照，不是真相。** 真相在 `t_wallet_flow`，理论上任何时刻都能用流水重算出余额。对账就是干这个的。

#### `t_credit_log` 信誉分流水

每次加减分一行：`change_value`、`balance_after`、`reason`（完成任务/超时/被驳回/邀请/人工调整）。

---

### 3.2 任务域

#### `t_task_category` 分类

7 条固定数据：应用试玩、注册下载、问卷调研、游戏试玩、内容体验、探店打卡、其他。

`t_task.category_id` 指向它。**关联查询必须用 `LEFT JOIN`**，因为 `category_id` 默认是 0（未分类），而分类表里没有 id=0。

#### `t_task` 悬赏任务（悬赏主发布的）

这张表字段最多，核心几组：

| 组 | 字段 | 说明 |
|---|---|---|
| 归属 | `publisher_id` | 发布者 user_id |
| 内容 | `title` / `cover` / `intro` / `steps`(jsonb) / `rules` | `steps` 存步骤 JSON |
| 定价 | `unit_price` / `service_fee_rate` | 单价、平台服务费率 |
| 名额 | `total_quota` / `taken_quota` / `finished_quota` / `remain_quota` | 四个计数 |
| 限制 | `limit_per_user` / `age_limit` / `deadline_minutes` | 每人次数、年龄、提交时限 |
| 状态 | `audit_status` / `status` | 审核态 + 上架态 |
| 运营 | `fast_review` / `top_until` / `weight` / `view_count` | 快审、置顶、权重、浏览数 |

> **名额为什么要有 4 个计数**：`total` 是上限，`remain` 是抢购的热点（`remain_quota > 0` 才允许报名），`taken` 便于统计转化，`finished` 是真正完成的量。四个冗余换查询性能。

#### `t_task_order` 报名单（整个系统的核心表）

用户 × 任务 = 一单。唯一索引 `uk_task_user (task_id, user_id)` 保证不能重复报名。

8 个状态：

| 值 | 状态 | 谁能改 |
|---|---|---|
| 1 | 进行中 | 报名时写入 |
| 2 | 待审核 | 用户提交凭证 |
| 3 | 已通过 | 悬赏主/平台审核 |
| 4 | 已驳回 | 悬赏主/平台审核 |
| 5 | 已超时 | 定时任务 |
| 6 | 已结算 | 结算任务（钱到账） |
| 0 / 7 | 待接单 / 已取消 | 预留 |

| 关键字段 | 说明 |
|---|---|
| `order_no` | 业务单号 `TO20261125...`，对外唯一标识 |
| `publisher_id` | **冗余**存发布者，避免查订单还要 JOIN 任务表 |
| `amount` | 成交时锁定的赏金（后续任务改价不影响已报名的单） |
| `deadline_at` | 报名时刻 + 任务的 `deadline_minutes` |

> `amount` 冗余的意义：悬赏主事后「加价」，已报名的单仍按原价结算，不会因为改价导致平台多付钱。

#### `t_task_submission` 提交凭证（与 order 1:1）

| 字段 | 说明 |
|---|---|
| `order_id` | 指向订单 |
| `user_id` | 冗余 |
| `images` | **jsonb**，形如 `["/files/2026/11/24/a.jpg"]` |
| `content` | 文字说明 |

> 存**相对路径**不存完整 URL。电脑 IP 一变，绝对 URL 全失效；相对路径由客户端拼当前 baseUrl，永远对。

### 3.3 资金域

#### `t_wallet_flow` 资金流水（账本）

**这是全库最重要的表。** 规则：

- 余额只能由流水驱动，禁止直接 `UPDATE t_wallet.available`
- 每条流水有 `biz_no`（业务幂等号），唯一索引，防止重复记账
- `balance_after` 存变动后快照，便于对账时定位

`biz_type` 枚举：`TASK_INCOME` / `INVITE_REWARD` / `WITHDRAW` / `MEMBER` / `PROMOTION` / `ADJUST`

#### `t_withdraw` 提现单

用户申请 → 冻结余额 → 人工审核 → 打款 → 扣冻结。

| 字段 | 说明 |
|---|---|
| `amount` / `fee` / `actual_amount` | 申请额、手续费、实际到账 |
| `channel` / `account` / `account_name` | 支付宝/微信/银行卡 |
| `status` | 0待审 1通过 2打款中 3成功 4失败 5驳回 |
| `third_no` | 支付宝转账单号 |
| `audit_by` / `audit_at` / `paid_at` | 审核与打款轨迹 |

#### `t_pay_order` 支付订单

充值、买会员、买增值服务都走它。`biz_type` 区分，`third_no` 存支付宝交易号（唯一，防重复回调）。

#### `t_promotion_order` 增值服务订单

置顶、定时置顶、自动刷新、刷新包、置顶包、加价、加量、快审——**8 种付费服务**。

| 字段 | 说明 |
|---|---|
| `type` | 8 种类型之一 |
| `qty` / `unit_price` / `amount` | 数量、单价、总价 |
| `effect_start` / `effect_end` | 生效区间（置顶到期、刷新包有效期） |

> 这张表是**平台唯一收入来源**。`t_task` 上的 `top_until` / `fast_review` 是它的"快照"，真正扣费记录在这里。

### 3.4 增长域

#### `t_invite` 邀请关系

`inviter_id`（谁邀请的）、`invitee_id`（被邀请的人，唯一）、`reward_amount`、`reward_status`。

#### `t_message` 站内信

`user_id` + `type`（系统/任务/钱包/审核/活动）+ `is_read`。

## 四、三条跨表规则

### 规则 1：余额 = 流水的累加

```
t_wallet.available  ≈  Σ(t_wallet_flow where direction=1) - Σ(direction=-1)
```

任何直接改 `t_wallet` 而不写流水的代码都是错的。对账任务的职责就是验证这个等式。

### 规则 2：没有物理外键，一致性靠应用层

原因：写性能、分库分表、DDL 灵活性。代价是可能出现"孤儿数据"（`category_id=99` 不存在）。缓解手段：

- 建表时用 `NOT NULL DEFAULT 0` 而不是可空
- 查询用 `LEFT JOIN`，代码里对空值兜底
- 关键唯一性用唯一索引兜住（如 `uk_task_user`）

### 规则 3：软删除 + 触发器

- 业务表有 `deleted SMALLINT`，MyBatis-Plus 的 `@TableLogic` 自动过滤
- `updated_at` 由 `set_updated_at()` 触发器维护，覆盖 7 张表，应用层不用手写
